<root_cause_analysis>
**Bug 1 (dialog height):** `DialogContent` in `CreateCompanyDialog.tsx` (line 203) has no `max-h`/`overflow` class, so the dialog grows to fit content instead of capping and scrolling. The established fix pattern already exists elsewhere in this codebase — apply the same classes used by sibling create-entity dialogs:
- `src/pages/VendorManagementPage/components/CreateVendorDialog.tsx:442` — `className="max-w-lg max-h-[90vh] overflow-y-auto p-0"`
- `src/pages/MsaPage/layouts/CreateMSADialog.tsx:1088` — `"rounded-2xl p-6 gap-6 max-h-[90vh] overflow-y-auto"`
- `src/pages/EvaluationManagementPage/components/CreateEvaluationDialog.tsx:542` — `className={cn("max-h-[90vh] overflow-y-auto p-0", {...})}`

None of these sibling dialogs use a sticky header/footer split — the whole `DialogContent` (header + body + footer together) gets `max-h-[90vh] overflow-y-auto` and scrolls as one unit. Match this exact established convention; do not invent a new sticky-header pattern.

**Bug 2 (Subscription Duration not persisting):** `subscriptionDurationOptions` (lines 129-135) is the only options array in this dialog using **numeric** `value`s (`1, 2, 3, 4, 5`), while the working `subscriptionOptions` (Subscription Plan) and `currencyOptions` (Currency) both use **string** values. Radix's underlying `@radix-ui/react-select` types `Select.Item`'s `value` prop as `string` and the shared `TextSelect` wrapper (`src/components/layouts/FormInputs/TextSelect.tsx`) types its own `options`/`value` props as `string` too — this dialog is the only caller violating that contract by passing numbers. This causes the "selected item text mirrors into the trigger" logic to behave inconsistently for this field only, matching exactly what's observed: the other two string-valued selects work, this number-valued one doesn't.

Fix: make `subscriptionDurationOptions` use string values (`"1"`..`"5"`), matching the working selects' convention exactly. Cascade this through:
- `defaultValues.duration` (line 66): `1` -> `"1"`
- yup schema (lines 35-39): `duration: yup.number().positive().integer().required(...)` -> `duration: yup.string().required("Subscription duration is required")` (the numeric `.positive()`/`.integer()` checks are redundant once the value is constrained to one of 5 fixed enum strings from a closed select — no free-form input exists for this field)
- `createCompany` mutationFn's `transformedData` (line 94): cast back to a number at submit time — `duration: Number(data.duration)` — so the `POST /onboarding/company` payload keeps sending a number, unchanged from current backend-facing behavior.
</root_cause_analysis>

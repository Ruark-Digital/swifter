**Task 1 root cause** (`@adexdsamson/forge` v1.1.0, `node_modules/@adexdsamson/forge/dist/index.esm.js:460`): `Forger` wraps its field in `memo(ForgerController, deepEqual)`. `deepEqual` (line 179) compares plain functions via `Object.keys(fn)`, which is always `[]` — so two different function references (e.g. a new inline closure created each render via `useCallback`) always compare as "equal", freezing the field at its FIRST render's closure forever. This is exactly the pattern already documented in project memory as `forge-memo-freezes-inline-component-closures`. In `OnboardingPage/index.tsx` (current), `PasswordInput`/`ConfirmPasswordInput` are built via `useCallback` closing over `showPassword`/`showConfirmPassword`, and passed as `<Forger name="password" component={PasswordInput} />` with NO other props on that Forger — so the entire Forger memoizes as "unchanged" on every toggle click, and the input never re-renders with the new `type`.

The **working pattern already used elsewhere in the same folder** (`src/pages/OnboardingPage/components/VendorStep1Form.tsx`, `PmOnboardingForm.tsx`) passes `component={TextInput}` (a stable, module-scope reference) with `type={showPassword ? "text" : "password"}` and `endAdornment={...}` as explicit Forger props. Since `type` is a primitive string, `deepEqual`'s top-level per-prop comparison (`val1 !== val2`) correctly detects the change and forces a re-render. Task 1 replicates this exact working pattern.

**Task 3 root cause** (`src/components/ui/multiselect.tsx`): the `MultipleSelector` component (backing `TextMultiSelect`, used by Solicitation's Step5Form vendor picker, Evaluation's Step2Form evaluators picker, and `RoleComboField`) renders 4 native buttons with no `type` attribute: the `PopoverTrigger`'s `<Button ref={ref} {...props} onClick={handleTogglePopover} ...>` (~line 274), the per-tag remove `<button onClick={() => handleUnselect(option)}>` (~line 306), the "+N more" clear `<button onClick={handleClearAll}>` (~line 335), and the "clear all" `<button onClick={handleClearAll}>` (~line 356). Per HTML spec, a `<button>` with no `type` defaults to `type="submit"`. `Forge` (`node_modules/@adexdsamson/forge/dist/index.esm.js:563-795`) renders a real `<form onSubmit=...>` on web. Clicking any of these 4 buttons while nested inside a Forge `<form>` (e.g. opening the vendor dropdown, or removing a selected vendor tag) fires native form submission — matching the reported "auto-submits without clicking Publish" symptom on BOTH the Solicitation and Evaluation flows, since both use the same shared `TextMultiSelect` component. Confirmed no `type` prop is passed through from `TextSelect.tsx`'s `<MultipleSelector ... />` call either. `Button` (`@/components/ui/button.tsx`) does not default its own `type` — it spreads `{...props}` onto a native `<button>`.

**Task 4 root cause** (`src/pages/UserManagementPage/UserManagementPage.tsx:341,351`): `handleFilterChange` (used by both the "Role" and "Status" dropdown filters) calls `navigate(\`/dashboard/users?${params.toString()}\`, { replace: true })`. The actual registered route (`src/routes/index.tsx:296`) is `/dashboard/user-management` — confirmed as the correct path used consistently everywhere else in the codebase (`src/lib/navigation.ts:364`, `src/layouts/Header.tsx:36`, `src/hooks/useSEO.ts:67`, `src/components/layouts/RoleBasedDashboard/index.tsx:89,91,95`, `src/utils/sitemapGenerator.ts:69`). Navigating to the nonexistent `/dashboard/users` fails to match any route under the `/dashboard` parent, which falls through to that parent route's `errorElement={<RouteErrorFallback />}` (`src/routes/index.tsx:133`, backed by `src/components/layouts/Error/index.tsx`) — replacing the entire dashboard layout with a generic "Oops, Something went wrong" page. This is React Router's own route-matching fallback, not a thrown JS exception, which is why nothing appears in the console — matching "crashes the app... no error logged to the console" exactly. Selecting Status reproduces the same failure (same handler) but wasn't reported; fixing the shared root cause fixes both.

**Task 2 investigation** (`src/pages/CompaniesPage/CompanyDetailPage.tsx`): the `moduleSchema` (`yup.object().shape({ evaluationsManagement: yup.boolean(), ... })`), `ModuleToggle` component, and `ForgerController`'s web `onChange` wiring were all traced end-to-end and correctly pass a plain boolean through on every toggle click — there is no bug in the click-handling path itself. The exact quoted error text (`evaluationsManagement must be a \`boolean\` type, but the final value was: \`{ "enabled": "true" }\`.`) is yup's default type-error message format, and it appears for MULTIPLE untouched module fields simultaneously the moment ANY single toggle is clicked. This only happens because `usePersist` (`node_modules/@adexdsamson/forge/dist/index.esm.js:915`) watches the WHOLE form and re-runs `handleSubmit(handleModuleSubmit)()` — i.e. validates every field — on ANY single field change. The only way one toggle click can produce simultaneous errors on OTHER, untouched fields is if those other fields are already holding a non-boolean shape (e.g. `{ enabled: "true" }`) at load time, from `defaultValues`/`reset()` assigning `portalSettingsData.<field>` directly without coercion (lines 296-308, 313-329). Task 2 defensively normalizes every module field to a real boolean at the point it enters the form, regardless of the exact upstream shape, which is what the QA description explicitly asks for ("toggling sends an actual boolean... yup schema validates correctly... no raw validation error text renders").
